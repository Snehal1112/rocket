# Factory driver commits plan series

Spec: `docs/superpowers/specs/2026-10-14-factory-driver-commits-design.md` (decisions 1 to 16, section "Plan shape"). It makes the factory write every commit and every merge or sync message through `dev-workflow-skills:1-git-commit`, adds GitHub issue references to those commits, and wires the Rocket knowledge base into builders, reviewers and a post-merge refresh.

Run the plans one at a time, in order, in a normal session (not as a factory job: this changes the driver, and `config.toml`, `Cargo.toml` and the harness rules are in `risk_paths`). Each plan has at most 3 tasks and ends with a `Next plan:` line. Do not start a plan before the previous one is merged. Harness rules apply to every plan: `cargo ... -j4`, never `--workspace` or `--all`, never set `CARGO_TARGET_DIR`, explicit `git add <paths>` and a pathspec commit, and every commit goes through the `dev-workflow-skills:1-git-commit` skill.

## Notes for whoever runs these

- Plans 02 to 07 are written one at a time, each after the previous plan is merged. Later plans call the signatures the earlier ones really produced, so writing them all up front would leave assumed names, which is what the v3 series had to reconcile afterwards.
- Plan 01 is the authority for the git layer signatures: `stage_all`, `worktree_is_clean`, `commits_above`, `commit_staged`, `staged_report`, and the types `CommitInfo` and `StagedReport`.
- The open points from the spec still stand: whether KB edits are committed automatically (the user's "yes please go ahead" on 2026-10-14 was read as yes, which is an assumption to confirm; plan 07 adds it behind a config flag that stays off until the first runs look right) and the first `kb_budget_weighted` value (a guess of 150000 until the real run).
- Start with plan 01.
- Notes carried from the plan 02 final review, for the plans named:
  - Plan 03: the per-run committer cap needs `budget_weighted = Some(commit_budget_weighted)` and `used_before = 0`. `with_limits` in `factory-engine/src/specs.rs` sets the job cap and the job's spent tokens, so do not reuse it unchanged for the committer. Set `env = [("HARNESS_GATE","0")]` and `strict_mcp = true` on the committer spec only; task runs use `tools = "Bash,Read,Skill"`; message-only runs need their own read-only `--tools` and `--allowedTools` lists, set consistently. The standing answers, the commit style line and the precomputed step 1 and 1b wording go in `commit-context.md`.
  - Plans 03 and 04: `ClaudeRunner` adds `spec.env` on top of the driver's own environment, so a driver started with `HARNESS_GATE=0` leaks it to builders and reviewers. Consider `env_remove("HARNESS_GATE")` for every agent except the committer.
  - Plan 05: `factory-committer.md` lists "the floor sha" and "the issue footer" as inputs for every run kind, but merge and sync runs have neither (the driver appends the footer). The merge and sync prompt must say so outright.
  - Plan 06: `kb_path` is not expanded, so `~/...` stays literal. Expand it where it is read, or document absolute paths only.
  - Known and old: `cargo clippy -p factory-agent -- -D warnings` fails on three lines (claude.rs:52, runner.rs:43, stream.rs:108). Clear them in a small cleanup before any plan adds a clippy gate for that crate.
- Notes carried from the plan 03 final review, for the plans named:
  - Plan 04: call `Engine::commit_step(&Worktree, &CommitRequest)` and handle `CommitOutcome::{Committed, NothingStaged, Park}` (call `Engine::park` on `Park`). The "builder committed on its own" guard (tip moved during the builder run) must run before `commit_step`. Map `NothingStaged` to the "changed nothing" parks. `CommitRequest.goal` and `task_title` need real values (the fallback subject uses `task_title`). The floor is the base in round 1 and the last reviewed head in fix rounds. For the `Ruling: task N commit amended task K commit <old> to <new>` audit line, `Committed` carries only the new tip: have plan 04 call `commits_above(floor, tip)` before and after, or extend `Committed` with before and after lists and the fallback reason. Also check the job budget before `commit_step`, because the committer's per-run cap (60000, two runs) sits outside the job cap.
  - Plan 05: `commit_step` cannot serve merge and sync (no staged changes). Reuse `validate_message`. `committer_spec` hard-codes `tools = "Bash,Read,Skill"` and `HARNESS_GATE=0`, so message-only mode needs its own spec builder with a read-only `--tools` and `--allowedTools` set consistently. Update the spec's section 5 wording: it names a `Committer` port, but the engine uses the `AgentRunner` port.
  - Plan 06: `CommitRequest` needs `issues`, and `validate_message` needs an issues argument for the `Relates to` footer check; the committer prompt must carry the footer text (the agent file already says to use it when named).
  - Repo hygiene (not in a plan): `.claude/settings.local.json` is ignored only by the user's global git ignore, so `stage_all` and the fallback commit could stage it on another machine. Add it to the repo `.gitignore` when the user agrees.
