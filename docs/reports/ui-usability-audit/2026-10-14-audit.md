# Rocket UI usability audit — 2026-10-14 (baseline, partial)

## Method
Falsifiable claims, each tested with a named instrument. Findings without an instrument are marked *unverified*.

| Layer | Instrument | Covers |
|---|---|---|
| Static | grep counts over 321 non-test `.tsx` files | a11y attributes, tiny text, motion, i18n |
| Runtime | axe-core (WCAG 2.2 AA + best-practice), Chromium 1440x900, light and dark | home view; after opening tree items |
| Runtime | Tab-order probe (25 stops), target-size and font-size census | keyboard path, hit targets |
| Timing | Playwright wait on splash removal | time to first usable UI |

## Limits (read before trusting numbers)
- The frontend ran against `e2e/helpers/tauri-mock.js`, which is incomplete (event plugin and several `list_*` commands were missing). I patched it in a scratch file. Views fed by mocked data are shallow; "Try again" as the first Tab stop is likely a mock-induced error state.
- Only 2 views were scanned (home, after tree clicks). Request editor, response, environments, git, assistant, flow, contracts and load-test are NOT covered.
- axe finds roughly a third of WCAG issues. Zero violations would not mean accessible. No screen-reader or task-based user testing.
- Single run per cell, no variance estimate. Splash timing comes from a headless, software-rendered browser.

## Confirmed findings (instrumented)
| # | Finding | Evidence | Severity |
|---|---|---|---|
| 1 | Forced splash blocks the app about 11.6 s on every launch. The Lottie is 8 s plus a 1 s lift-off; there is no skip, no timeout and no `onerror`, so a failed asset load blocks the app permanently | measured 11.6 s; `src/components/SplashScreen.tsx` has no fallback; `motion-reduce` appears in 1 file | High |
| 2 | Dark-theme `text-destructive` is 2.67:1 against the background (needs 4.5:1). Token `--destructive: 5 99% 37%` at `src/globals.css:229`, used as text in 129 places | axe, 16 nodes | High |
| 3 | Muted text fails AA at small sizes: dark 4.06:1, light 4.34:1, and 3.75:1 on tab labels (10-12 px) | axe color-contrast | Medium |
| 4 | Four tab items have no `tablist` parent; the Preview/Edit trigger's `aria-controls` points at a missing id | axe critical: aria-required-parent, aria-valid-attr-value | High for screen readers |
| 5 | Sidebar `role="tree"` contains a `button[aria-haspopup]` child, which is disallowed; nested interactive element in a `.py-3` row | axe critical + serious | Medium |
| 6 | Four icon buttons (e.g. New Collection) are 20x20 px, below the 24 px WCAG 2.2 minimum; 9 of 29 interactive elements are under 24 px | axe target-size; census | Medium |
| 7 | No landmarks and no `h1` | axe region, page-has-heading-one | Low (desktop app) |
| 8 | 77 of 321 files use 9-11 px text; the home view alone has 5 elements at 10-11 px | grep + census | Medium |
| 9 | The sidebar resize handle is a focusable `div`, 1 px wide, with no visible focus ring | Tab probe | Low |
| 10 | After the last stop, focus lands on `body` | Tab probe stop 23 | Low, needs recheck |

## Positive signals
- Visible focus ring on 21 of 23 stops probed.
- 127 files carry `aria-label`; 24 use confirm dialogs.
- Light and dark themes fail on mostly the same rules, so there is no theme-specific regression except #2.

## Unverified (hypotheses to test next)
- H1: error states give a recovery path (114 files show errors; only 5 use `aria-live` or `role=alert`).
- H2: only 3 files call `toast(`, so success feedback may be inconsistent.
- H3: no i18n (0 files), so no localization path.
- H4: layouts below about 1100 px wide break.

## Recommended next steps
1. Fix #1, #2 and #4 first (small, high value): add a splash timeout of about 1.5 s with skip-on-keypress, lighten the dark destructive text token, and wrap the tabs in a `tablist`.
2. Extend the Playwright mock to cover every startup command, then scan every top-level view and the main dialogs.
3. Run a task-based test with 5 users on three tasks (send first request, create environment, commit via Git UI), measuring time on task and errors.
